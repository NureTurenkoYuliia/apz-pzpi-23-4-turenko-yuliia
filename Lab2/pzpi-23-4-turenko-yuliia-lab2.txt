2 ЗАВДАННЯ
     Необхідно розробити мобільний програмний застосунок для будь-якої поширеної на сьогодні мобільної платформи. Мобільний застосунок повинен бути частиною системи і повинен взаємодіяти з нею. Для реалізації програмного застосунку можна використовувати технології для реалізації програмного забезпечення для мобільних платформ. Звіт повинен містити опис прийнятих інженерних рішень. У ньому повинна бути показана будова мобільного застосунку та його взаємодія з іншими частинами системи.
     
3 ОПИС ВИКОНАНОЇ РОБОТИ
     Для реалізації мобільного клієнта було обрано Flutter із використанням мови програмування Dart. Такий підхід дозволяє створити кросплатформений застосунок із єдиною кодовою базою, сучасним інтерфейсом та підтримкою швидкої розробки. Flutter також забезпечує зручну інтеграцію з REST API та дозволяє легко масштабувати проєкт у майбутньому. Архітектура мобільного застосунку побудована за принципом логічного розділення відповідальностей між шарами інтерфейсу, бізнес-логіки та роботи з API, а також розробляється з дотриманням принципів чистої архітектури та модульного підходу. Структура застосунку поділена на окремі логічні частини: екрани інтерфейсу (screens), компоненти (widgets), сервіси роботи з API (api/services), моделі даних (models) та допоміжні утиліти (utils). Такий підхід забезпечує зрозумілу організацію коду та спрощує подальше розширення системи. Є окремі reusable-компоненти інтерфейсу, що дозволяють повторно використовувати код та дотримаватися принципів SOLID.
     Мобільний застосунок взаємодіє з backend-системою через HTTP-запити до ASP.NET Core Web API. Для роботи з API використовується бібліотека Dio, а авторизація реалізована через JWT токени з локальним збереженням access та refresh token. Тестування застосунку виконується за допомогою Android Emulator, підключеного до Flutter-проєкту через Visual Studio Code. 
     У мобільному клієнті реалізовано основні функціональні модулі системи. Було створено сторінки авторизації та реєстрації користувача, головну сторінку зі списком акваріумів, сторінку деталей акваріума та приладів, модулі керування правилами сповіщень (Alarm Rules), запланованими командами (Scheduled Commands), а також сторінку повідомлень (Notifications). Реалізовано створення, редагування, видалення та перегляд відповідних сутностей із використанням діалогових вікон та інтерактивних елементів інтерфейсу. 
     Головний екран мобільного застосунку, реалізований у файлі home_screen, виступає центральною точкою взаємодії користувача із системою (код В.1). Сторінка забезпечує отримання списку акваріумів через backend API, їх відображення у вигляді окремих інформаційних блоків та навігацію до детальної інформації про вибраний акваріум. Також реалізовано функції створення, редагування та видалення акваріумів із автоматичним оновленням інтерфейсу після змін. У верхній частині екрану розміщені кнопки для переходу до повідомлень та зміни мови інтерфейсу. Для покращення користувацького досвіду застосовано локалізацію текстів, обробку станів завантаження та повідомлення про помилки або відсутність даних.
     Для покращення зручності використання системи було додано підтримку інтернаціоналізації. Застосунок підтримує українську та англійську мови за допомогою бібліотеки easy_localization. Реалізовано окремий компонент LanguageButton для перемикання мови (код В.2), який використовується на різних сторінках застосунку. Це дозволяє динамічно змінювати мову інтерфейсу без перезапуску застосунку.
     На UML діаграмі прецедентів (Use Case Diagram) показано основні сценарії взаємодії користувача із системою (рис. Б.1). Користувач може виконувати авторизацію, працювати з акваріумами та приладами, переглядати сенсорні дані, створювати правила автоматичного реагування, керувати командами та переглядати повідомлення системи. Також передбачено зміну мови інтерфейсу застосунку.
     На UML діаграмі компонентів (Component Diagram) показано основні складові мобільного застосунку та їх взаємодію між собою (рис. Б.2). Інтерфейс користувача складається зі сторінок (UI Screens) та окремих віджетів (Widgets Components), які взаємодіють із API-шаром. API-компоненти відповідають за роботу з конкретними модулями backend-системи: авторизацією, акваріумами, приладами, правилами сповіщень, командами та повідомленнями. Окремо виділено модуль локалізації та компонент збереження токенів авторизації.
     Для забезпечення функціональності системи було реалізовано набір основних сторінок мобільного застосунку. До них належать сторінки реєстрації та входу в систему, головна сторінка зі списком акваріумів, сторінка деталей акваріума та приладів, сторінки правил сповіщень (Alarm Rules), команд керування (Commands) та повідомлень користувача (Notifications). Кожен модуль підтримує створення, редагування, видалення та перегляд відповідних сутностей.
     На UML діаграмі діяльності (Activity Diagram) показано процес авторизації користувача (рис. Б.3). Після запуску застосунку система перевіряє наявність токена доступу. Якщо токен існує, користувач автоматично переходить на головну сторінку. Якщо токен відсутній, відкривається сторінка входу, де після успішної перевірки облікових даних виконується збереження токена та перехід до основного інтерфейсу застосунку.
     Діаграма взаємодії (Interaction Overview Diagram) демонструє загальний сценарій роботи мобільного застосунку (рис. Б.4). Після запуску система перевіряє наявність авторизації користувача та відкриває відповідний екран. Далі застосунок взаємодіє з backend API для отримання списку акваріумів, приладів і сенсорних даних. Користувач може виконувати операції керування пристроями, правилами та командами, після чого інтерфейс оновлюється відповідно до отриманих даних.
     У ході виконання роботи було використано інструмент штучного інтелекту. Назва інструменту та версія: ChatGPT 5.3.
     Перший запит до ШІ був зроблений для реалізації авторизації та роботи з JWT-токенами у мобільному застосунку Flutter (запит В.3). Мета: створення логіки взаємодії з backend API, збереження access/refresh token та автоматичного переходу між екранами після успішної авторизації. Внесок автора: отриманий код був перевірений, адаптований під структуру проєкту та доповнений власною логікою обробки помилок і навігації.
     Під час розробки сторінок був запит до ШІ для правильної реалізації сторінок керування приладами, правилами та запланованими командами (запит В.4). Мета: створення структурованих екранів із CRUD-операціями, інтеграцією з backend API та відображенням даних у вигляді окремих інформаційних блоків. Внесок автора: отриманий результат був доопрацьований, перевірений через тестування API та змінений відповідно до бізнес-логіки системи та гарного UI відображення.
     Також був зроблений запит до ШІ для реалізації інтернаціоналізації мобільного застосунку українською та англійською мовами (запит В.5). Мета: налаштування інтернаціоналізації за допомогою пакету easy_localization, створення системи перекладів і кнопки перемикання мов у спільному компоненті інтерфейсу. Внесок автора: отримане рішення було перевірене на працездатність та змінене відповідно до структури інтерфейсів і стилю застосунку.
